1. 總覽與角色分工

本專案採 Git Flow 三層分支模型，搭配 GitHub Pull Request 與 必過 CI 閘。Review 政策為 self-merge 容許， 但所有 PR 必須通過 GitHub Actions 的 lint / typecheck / build / test 才能合併。

角色與責任

FE
前端負責人 × 1
擁有 oct/frontend/。負責 Vite + React UI、API client、UX。 PR 主要審查者。M2 之後加入 Monaco Editor 與題目作答介面。
BE1
後端 — 認證 / 使用者
擁有 oct/backend/src/routes/auth.*、users.*、 相關 schema 與 migration。
BE2
後端 — 題目 / 提交
擁有 routes/problems.*、routes/submissions.*、 題目相關 schema。M2 接判題 worker。
BE3
後端 — Infra / 共用層
擁有 backend/src/db/、env.ts、 docker-compose、.github/workflows/、CI / 部署。

核心約定

  • main 永遠可部署，僅由 develop 的 PR 合入（每個 milestone 結束時）。
  • develop 是整合分支，所有 feature PR 都打到這裡。
  • 所有 PR 必須通過 CI；CI 紅燈的 PR 一律 不准 merge。
  • 每人只動自己 ownership 內的檔案；要動別人區域時開 issue 討論或 ping 對方。
  • 使用 Squash & Merge 保持 develop / main 線性歷史。

2. Branch 模型

Branch用途誰可以 push受保護
main 永遠可部署的穩定版本，每個 milestone tag 一次 僅 PR (from develop) protected 禁止 force-push、刪除；require CI
develop 整合分支，所有 feature 都 PR 到這裡 僅 PR (from feature/*) protected 禁止 force-push、刪除；require CI
feature/<name>-<desc> 個人開發、新功能 個人 無限制；merge 後刪除
fix/<name>-<desc> 非緊急 bug fix（從 develop 切出） 個人 無限制；merge 後刪除
hotfix/<desc> main 上的緊急修復（demo 前壞掉等） BE3 / 主 reviewer 從 main 切，merge 回 main + develop

3. 命名規則

Branch 命名

# 格式
<type>/<owner>-<short-kebab-desc>

# 範例（owner 用英文短碼，避免中文與底線）
feature/be1-auth-login
feature/be2-problem-crud
feature/be3-ci-workflow
feature/fe-problem-list
fix/be1-jwt-expired-edge-case
hotfix/healthcheck-ipv6
  • type：feature / fix / hotfix / chore / docs
  • owner：fe / be1 / be2 / be3 — 一眼看出主責人
  • desc：英文小寫、kebab-case、3–6 個詞，描述「做什麼」而非「為什麼」
  • 分支壽命建議 ≤ 5 天，太久請拆小

Tag 命名（main 上的 release）

v<major>.<minor>.<patch>-<milestone>
# 範例
v0.1.0-M1   # M1 骨架完成
v0.2.0-M2   # M2 認證 + 判題
v0.3.0-M3   # M3 K8s 部署
v1.0.0-M4   # M4 期末驗收版

4. 日常開發流程

  1. 同步 develop 並開新分支 
    git switch develop
git pull --ff-only
git switch -c feature/be1-auth-login
  2. 開發 → 經常 commit / push

    commit message 用簡短一行（見 §7）。push 一次，遠端就會建立追蹤分支。

    git add -A
git commit -m "add login route"
git push -u origin feature/be1-auth-login
  3. 發 PR 到 develop

    用 GitHub UI 或 gh CLI。base 一定選 develop，不要打到 main。

    gh pr create --base develop --title "Add JWT login route" --body-file .github/PULL_REQUEST_TEMPLATE.md
  4. 等 CI 全綠

    GitHub Actions 自動跑 lint / typecheck / build / test，紅燈不能 merge。

  5. Self-merge（Squash & Merge）

    確認 diff 無誤、CI 綠 → 點 Squash and merge。merge 後 GitHub 會自動刪除 feature branch。

  6. 本地清理 
    git switch develop
git pull --ff-only
git branch -d feature/be1-auth-login

每天一開機要做的事

git switch develop && git pull --ff-only
# 然後 rebase 到自己的 feature branch 上，避免合併時衝突累積
git switch feature/be1-auth-login
git fetch origin
git rebase origin/develop

5. Pull Request 規則

5.1 PR 標題

  • 一句話、動詞開頭、英文：Add JWT login route / Fix health check IPv6 timeout
  • Squash & Merge 後會變成 develop 上的 commit message，所以要寫清楚
  • 不強制 conventional commits；想加 prefix 也 OK，但保持團隊一致

5.2 PR 描述模板

## What
# 一句話說明這個 PR 做了什麼

## Why
# 為什麼要做（連結 issue：Closes #12）

## How
# 主要實作策略 / 設計決策

## Test plan
# - [ ] 跑過 npm run build
# - [ ] 本地 docker compose up 確認 happy path
# - [ ] 列出新增 / 修改的 endpoint 與測試方式

## Notes
# - 是否動到 .env.example？（→ 通知所有人）
# - 是否新增 migration？（→ 通知所有人 reset DB）
# - 是否動到別人 ownership 的檔案？

建議在 repo 根目錄放 .github/PULL_REQUEST_TEMPLATE.md，開 PR 時 GitHub 會自動帶入。

5.3 PR 大小

大小diff 行數建議
小< 200理想，5 分鐘可 review 完
中200 – 400OK，但要分章節描述
大400 – 800盡量拆，無法拆就在描述加 reading order
過大> 800必須拆。可先合一個 stub PR 進 develop，再分階段補

5.4 Self-merge 注意事項

Self-merge 容許，但請守住三條底線

  1. CI 必須全綠：紅燈絕對不能 merge（branch protection 已強制）。
  2. 動到關鍵檔案要 ping 一個人：.env.example、docker-compose.yml、migrate.ts、schema.ts 變動時，在 PR 留言 @teammate ptal，等對方看過再 merge。
  3. 自己要再看一次 diff：開 PR 後切到 Files changed 頁，假設自己是 reviewer 重看一遍。

5.5 Merge 策略

  • feature → develop：Squash & Merge（壓成一個 commit，保持線性）
  • develop → main：Merge commit（保留 develop 的歷史軌跡）
  • hotfix → main：Squash & Merge，再 cherry-pick 到 develop
  • 關閉 GitHub repo 設定中的 Rebase merge，避免大家點錯

6. BE 三人並行策略

後端 3 人並行最容易踩雷的地方是 共用層（DB schema、env、共用 middleware）。 下面列出常見衝突點與避雷方式。

6.1 模組切割（避免動到別人檔案）

oct/backend/src/
├── server.ts            [BE3] 入口、plugin 註冊
├── env.ts               [BE3] env schema（變動需通知所有人）
├── db/
│   ├── client.ts        [BE3] connection pool
│   ├── schema.ts        [共用] 變動需 PR 開 review
│   └── migrate.ts       [BE3] migration runner
├── routes/
│   ├── auth.ts          [BE1] 登入 / 註冊 / JWT
│   ├── users.ts         [BE1] user CRUD
│   ├── problems.ts      [BE2] 題目 CRUD
│   ├── submissions.ts   [BE2] 提交 / 判題接口
│   ├── health.ts        [BE3] /api/health
│   └── ping.ts          [BE3] /api/ping
└── middleware/
    └── auth.ts          [BE1] JWT verify middleware

6.2 DB Schema 與 Migration 衝突

三條鐵律

  1. 每個人開獨立的 migration 檔。檔名用 timestamp 前綴： 20260510_add_users.sql、20260511_add_problems.sql。 永遠不要修改已 merge 的 migration。
  2. 新增欄位 / 表 → 開 issue 公告。在 issue tracker 留 [schema] label，3 位 BE 各 +1 確認後才 merge。
  3. 合到 develop 後通知群組：「我加了 problems 表，pull 完請跑 make rebuild 重建 DB」。

6.3 env 變動

  • 動到 .env.example / env.ts 的 PR 標題加 [env] 標記
  • 新增 env 變數要同時更新 .env.example 與 README 的環境變數表
  • 不可移除既有 env 變數（破壞別人本地環境）；要移除請另開 deprecation PR

6.4 共用 utility / type

  • 三人共用的 utility 放 backend/src/lib/，動到要 ping 全員
  • 共用 type 放 backend/src/types/，型別變動視為破壞性，PR 描述要列影響範圍

6.5 大重構先寫 RFC issue

動超過 3 個檔案的重構（換框架、換 ORM、改 plugin 結構）開一個 [rfc] issue， 簡述方案 / 影響 / 替代方案，等 24 小時讓其他 BE 反饋，再開實作 PR。

7. Commit message 風格

本專案 commit message 偏好極簡一行，不強制 Conventional Commits。 Squash & Merge 時會用 PR title 取代，所以 commit message 主要是給開發中的自己看。

✅ 好的 commit message

init
add login route
fix health timeout
update README
wip: schema draft

❌ 不需要的格式

chore: scaffold M1 skeleton (FE+BE+DB)

This commit adds the initial Docker
scaffolding including frontend,
backend, and Postgres...
  • commit 標題 ≤ 50 字，現在式祈使句（add / fix / update / remove）
  • 不需要 prefix（chore: / feat:）；想加也 OK，保持自己一致
  • WIP commit 用 wip: 開頭，避免別人誤以為已完成
  • 真的需要長說明時，commit body 留給特殊情境（hotfix 後寫事件追溯）

PR title vs commit message

commit message 是寫給自己看的開發痕跡 → 簡短。
PR title 會變成 develop 上的 squash commit → 完整、英文、動詞開頭。

8. Release / Merge to main

8.1 Milestone 完成時

  1. 確認 develop 所有功能皆已 merge、CI 綠、本地 make rebuild 重建可跑
  2. 開 PR：develop → main，title 例：Release v0.1.0-M1
  3. PR 描述列出本 milestone 所有 features (用 git log main..develop --oneline 抓)
  4. CI 綠後 Merge commit（保留歷史，不 squash）
  5. 本地切到 main、pull、打 tag、推 tag： 
    git switch main && git pull --ff-only
git tag -a v0.1.0-M1 -m "M1: minimal scaffold"
git push origin v0.1.0-M1
  6. GitHub Releases 頁手動建立 release，附 changelog 與 demo 截圖（給助教看）

8.2 main 受保護的設定

規則maindevelop
Require pull request before merging✅✅
Require status checks to pass (CI)✅✅
Require approvals0（self-merge 可）0
Require linear history❌（保留 merge commit）✅
Block force pushes✅✅
Allow deletions❌❌

9. CI / GitHub Actions

所有 PR 觸發 CI，CI 紅燈不能 merge。Workflow 放在 .github/workflows/ci.yml。

9.1 CI Jobs（PR 必過閘）

Job步驟失敗條件
frontend npm ci → npm run lint → npm run typecheck → npm run build 任一步 exit ≠ 0
backend npm ci → lint → typecheck → build → test（搭配 PG service container） 任一步 exit ≠ 0
compose-build docker compose build 確認兩個 image 都能 build build 失敗

9.2 Workflow 範例（簡化）

# .github/workflows/ci.yml
name: CI
on:
  pull_request:
    branches: [develop, main]
  push:
    branches: [develop, main]

jobs:
  frontend:
    runs-on: ubuntu-latest
    defaults:
      run:
        working-directory: oct/frontend
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: '20', cache: 'npm', cache-dependency-path: oct/frontend/package-lock.json }
      - run: npm ci
      - run: npm run lint
      - run: npm run typecheck
      - run: npm run build

  backend:
    runs-on: ubuntu-latest
    defaults:
      run:
        working-directory: oct/backend
    services:
      postgres:
        image: postgres:16-alpine
        env:
          POSTGRES_USER: oct
          POSTGRES_PASSWORD: oct
          POSTGRES_DB: oct
        ports: ['5432:5432']
        options: >-
          --health-cmd pg_isready --health-interval 5s
          --health-timeout 3s --health-retries 5
    env:
      DATABASE_URL: postgres://oct:oct@localhost:5432/oct
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: '20', cache: 'npm', cache-dependency-path: oct/backend/package-lock.json }
      - run: npm ci
      - run: npm run lint
      - run: npm run typecheck
      - run: npm run build
      - run: npm test

本地預跑 CI（避免推上去才發現紅）

每個子專案在 PR 前自己跑一次：

cd oct/backend
npm run lint && npm run typecheck && npm run build && npm test

11. 衝突處理 & Hotfix

11.1 Merge 衝突解法（rebase 派）

git switch feature/be1-auth-login
git fetch origin
git rebase origin/develop

# 衝突發生 → 修檔 → git add && git rebase --continue
# rebase 完才 push（因為歷史改寫了）
git push --force-with-lease origin feature/be1-auth-login

為什麼用 rebase 不用 merge

在 feature branch 上 git rebase develop 比 git merge develop 乾淨： 避免 feature branch 上多出 "Merge develop into feature/x" 這種雜訊 commit， 最後 squash 進 develop 時歷史比較線性。
但只在自己的 feature branch 上 rebase，永遠不要 rebase 已 push 並有人在用的共用分支。

11.2 Hotfix 流程（main 上線後壞掉）

  1. 從 main 切 hotfix/<desc>
  2. 修復 → commit → push → 開 PR 到 main
  3. CI 綠後 squash & merge 進 main、打新 tag v0.1.1-M1
  4. 立刻將 hotfix 的 commit cherry-pick 回 develop（不然 develop 會缺修正）： 
    git switch develop && git pull --ff-only
git cherry-pick <hotfix-commit-sha>
git push origin develop
  5. 在 group chat 公告：「main 已修，請大家 rebase develop」

11.3 走錯分支 / 想撤回

情境解法
commit 打到錯的 branch（還沒 push）git reset --soft HEAD~1 取回變更，切到對的 branch 再 commit
commit 打到錯的 branch（已 push）從正確 branch cherry-pick 過來，再從錯的 branch revert
已 merge 的 PR 要撤回GitHub UI 上點 Revert，會自動開反向 PR
不小心 push 了 .env立刻通知群組換密碼，git filter-repo 或 BFG 清歷史，force-push（這次例外）

12. 指令速查

12.1 日常 Git

# 開新 feature
git switch develop && git pull --ff-only
git switch -c feature/be1-auth-login

# 同步最新 develop（rebase 派）
git fetch origin && git rebase origin/develop

# 推到遠端
git push -u origin feature/be1-auth-login        # 第一次
git push                                          # 之後
git push --force-with-lease                       # rebase 後

# 看誰動了什麼
git log --oneline --graph --all -20
git log develop..HEAD --oneline                   # 我這支 branch 比 develop 多了什麼

# 清掉本地已 merge 的舊 branch
git branch --merged develop | grep -v develop | xargs -n1 git branch -d

12.2 GitHub CLI（gh）

# 開 PR
gh pr create --base develop --fill

# 看自己的 PR
gh pr list --author @me

# 在 CLI merge 自己的 PR
gh pr merge --squash --delete-branch

# 看 CI 狀態
gh pr checks
gh run list --branch feature/be1-auth-login --limit 5

12.3 Compose 速查（Makefile 已包好）

make bootstrap   # 複製 .env.example → .env
make up          # docker compose up -d --build
make logs        # 看所有服務 log
make ps          # 服務狀態
make psql        # 進 Postgres CLI
make rebuild     # clean + up（重置 DB volume）
make down        # 關閉
make clean       # down + 刪 volume
